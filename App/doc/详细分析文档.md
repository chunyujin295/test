## 1. 系统背景与架构概览

### 1.1 项目定位

MoldAI 是一个基于 C++/Qt6 的**摄影测量与三维重建桌面软件**。其核心能力是通过多视角图像进行：
- **空三解算（AT, Aerial Triangulation）**：特征检测 → 特征匹配 → SfM → 点云生成
- **三维重建（Reconstruction）**：从稀疏点云生成稠密三维模型
- **批量预处理（Batch Prepare）**：图像预处理与格式转换

### 1.2 架构总览

```
┌──────────────────────────────────────────────────────────────┐
│                        MoldAI App (上层应用)                    │
│  用户界面 → 提交 Job → 监控进度 → 展示结果                      │
└──────────────────────────┬───────────────────────────────────┘
                           │ 文件系统 (Job Queue Directory)
                           ▼
┌──────────────────────────────────────────────────────────────┐
│                  MoldAINode.exe (Engine 引擎层)                │
│                                                              │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  多线程调度核心                                        │    │
│  │  · searchPendingJobThread2   主调度循环               │    │
│  │  · searchUnnormaldRunningJobThread  异常任务监控      │    │
│  │  · execEngineTimeThread      引擎心跳上报             │    │
│  │  · execTaskTimeThread        Task 心跳管理            │    │
│  │  · DoCleanupLockFiles        残留锁清理               │    │
│  └─────────────────────────────────────────────────────┘    │
│                           │                                  │
│                QProcess::start()                             │
│                           ▼                                  │
│  ┌─────────────────────────────────────────────────────┐    │
│  │          MoldAITask.exe (Task 执行器)                 │    │
│  │  · RunSfM / RunFeatureDetection / RunReconstruction  │    │
│  │  · RunBatchPrepare / RunMatchPairs ...               │    │
│  └─────────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────────┘
```

### 1.3 为什么采用 Engine/Task 分离架构？

| 考量 | 说明 |
|------|------|
| **进程隔离** | Task 进程崩溃不会导致 Engine 崩溃，引擎可持续处理其他任务 |
| **资源回收** | 每次 Task 退出后操作系统回收全部内存/GPU 资源，避免算法库内存泄漏累积 |
| **并行扩展** | 未来可扩展到多机分布式：Engine 在主机，Task 分布在计算节点 |
| **独立部署** | Engine 和 Task 可独立更新，只要文件格式兼容 |
| **解耦通信** | 通过文件系统（非 IPC/Socket）通信，简化调试——直接查看文件内容即可判断状态 |

### 2.3 多线程架构设计

Engine 共启动 **5 个后台线程 + 1 个主线程（Qt 事件循环）**：

```
                    ┌─────────────────────────┐
                    │   Main Thread            │
                    │   QApplication::exec()   │ ← Qt 事件循环（信号槽、UI）
                    └─────────────────────────┘

┌───────────────────────┐ ┌──────────────────────┐ ┌───────────────────────────┐
│ Thread 1: 主调度        │ │ Thread 2: 异常监控     │ │ Thread 3: 心跳维护          │
│ searchPendingJobThread2│ │ searchUnnormald...    │ │ execEngineTimeThread       │
│                        │ │                       │ │                            │
│ 循环扫描:               │ │ 循环检测:               │ │ 每 1 秒刷新:                │
│   Pending/ → Running/  │ │   异常 Running 任务     │ │   Engines/<hostname>.json  │
│   Running/ → Task 执行  │ │   无主 .lock / .pid    │ │   包含: 当前任务、版本、状态  │
│                        │ │                        │ │                            │
│ 周期: ~1s (有任务阻塞)   │ │ 周期: 500ms-1s         │ │ 周期: 1s                   │
└───────────────────────┘ └──────────────────────┘ └───────────────────────────┘

┌───────────────────────┐ ┌───────────────────────────┐
│ Thread 4: Task 心跳    │ │ Thread 5: Lock 清理        │
│ execTaskTimeThread    │ │ DoCleanupLockFiles         │
│                       │ │                            │
│ 每 1 秒刷新:           │ │ 循环检查 toBeCleanedJobMap  │
│   task_def_N.json.pid │ │ 若 job 已结束 → 删除 .lock │
│   写入: PID, 活跃时间   │ │                            │
│                       │ │ 周期: 1s                   │
│ 周期: 1s              │ │                            │
└───────────────────────┘ └───────────────────────────┘
```

#### 线程间通信方式

这些线程之间**没有使用 mutex 或 condition_variable**，而是通过以下方式间接通信：

| 方式 | 示例 | 风险 |
|------|------|------|
| 全局变量轮询 | `gotNewPendingJobFile`, `bQuitingApplication`, `taskrunning` | 竞态条件 |
| 文件系统 | Lock 文件、Job 文件、Feedback 文件 | 相对安全 |
| `fpTaskLock` 指针 | 非 NULL 表示有任务正在被处理 | 多线程读写不安全 |

### 2.4 任务队列调度机制

这是 Engine 最核心的逻辑，由 `searchPendingJobThread2` 函数驱动。

#### 2.4.1 调度总循环（searchPendingJobThread2）

```cpp
void searchPendingJobThread2()
{
    while (true)
    {
        // ---- 守卫条件 ----
        if (bQuitingApplication) break;
        if (bNetworkPathAlreadyInvalid) break;

        // 条件 1: 如果 Engine 当前正在处理一个 task，跳过本轮
        if (gotNewPendingJobFile || !NewFileForRun.isEmpty())
        {
            sleep(1000ms);
            continue;
        }

        // 条件 2: 如果 Task 子进程正在运行，跳过本轮
        if (taskrunning)
        {
            sleep(1000ms);
            continue;
        }

        // 条件 3: 清理异常的 task lock
        if (fpTaskLock != NULL)
        {
            fclose(fpTaskLock);
            fpTaskLock = NULL;
        }

        // ---- 核心调度逻辑 ----
        // ★ 优先级 1：检查 Running 队列中是否有未完成的任务
        if (GetRunningTaskInRunningJob() != AI3D_SUCCESS)
        {
            // ★ 优先级 2：Running 队列为空，从 Pending 队列获取新任务
            GetPendingJob();
        }

        // 如果成功获取到了任务，执行它
        if (gotNewPendingJobFile && !NewFileForRun.isEmpty())
        {
            int retCode = ExecTaskFileV2();  // ★ 阻塞！直到子进程结束
            if (retCode == -1) { init(); }    // 执行失败则重置状态
        }

        sleep(1000ms);
    }
}
```

#### 2.4.2 Running 队列扫描（GetRunningTaskInRunningJob）

这个函数负责从 Running 队列中找出需要继续执行的任务。它的核心逻辑是：

```
遍历 Running/ 目录中的每个 Job 文件:

  ┌─ Job 文件是否以 .lock 结尾？ → 跳过

  ├─ Job 文件是否存在？ → 否 → 跳过

  ├─ 加载 Job → 读取 tasksmap

  ├─ Job 是否包含 taskdef0（未拆分的原始大任务）？
  │   ├─ 是（HasTaskDef0 == true）：
  │   │   ├─ 尝试获取 job 的排他锁 → 失败则跳过
  │   │   │
  │   │   ├─ taskdef0 未完成？
  │   │   │   └─ 锁定 task_def_0 文件，设置 NewFileForRun
  │   │   │
  │   │   ├─ 有 Pending 状态的 Task？
  │   │   │   └─ 锁定第一个 Pending Task
  │   │   │
  │   │   ├─ 有 Running 状态但未完成的 Task？
  │   │   │   └─ 尝试锁定它继续执行
  │   │   │
  │   │   ├─ 验证 task 文件存在 + feedback 状态为 RUNNING
  │   │   │
  │   │   └─ 更新 jobinfo，设置 gotNewPendingJobFile = true
  │   │
  │   └─ 否（非 taskdef0，即已拆分 / 不需要拆分的任务）：
  │       ├─ taskdef0 已完成？
  │       │   └─ 继续（正常流程）
  │       └─ 未完成？→ 跳过（等待拆分完成）
  │
  └─ 遍历下一个 Job
```

**关键代码片段**（CallEngine.cpp 第 1558 行）：

```cpp
// 判断是否包含 taskdef0（原始大任务，需要拆分）
if (jobinfo.tg.HasTaskDef0())
{
    // ... 处理需要拆分的任务（空三流程）
    // 从 taskdef0 开始，拆分出多个子任务（特征检测、匹配、SfM 等）
}
else
{
    // ... 处理已拆分 / 不需要拆分的任务
    // 直接找到第一个 Pending 的 Task 执行
}
```

#### 2.4.3 Pending 队列获取（GetPendingJob）

```
遍历 Pending/ 目录（已按优先级和时间排序）:

  ├─ 尝试对 job 文件加排他锁 (.lock)
  │   └─ 失败 → 其他引擎正在处理，跳过
  │
  ├─ 读取 job 信息 (projectFile_, blockItem_, tasksmap)
  │
  ├─ 构造 Running 目录中的目标路径
  │
  ├─ 将 Job 信息保存到 Running/ 目录
  │   └─ 失败 → 释放锁，跳过
  │
  ├─ 从 Pending/ 删除原 job 文件
  │
  ├─ 保存 feedback 文件（初始状态: RUNNING, 0%）
  │
  ├─ 对 task_def_0 文件加排他锁
  │
  └─ 设置 gotNewPendingJobFile = true, NewFileForRun = taskfile
```

### 2.5 Lock 文件互斥协议

Lock 文件是 Engine/Task 多进程互斥的核心机制。它的工作方式**类似于数据库的行级锁**。

#### 2.5.1 实现原理

使用 Windows API 的文件共享模式实现排他锁：

```cpp
FILE* fp = AICORE::File::FopenDenyWriteLockUtf8(filepath + ".lock");
```

这个函数内部使用 `_fsopen` 或 `CreateFile` 时指定**拒绝写入**的共享模式：
- **成功返回非 NULL 指针**：当前进程独占写入权，其他进程无法打开此文件写入
- **返回 NULL**：其他进程已持有该锁

#### 2.5.2 三级锁体系

```
┌──────────────────────────────────────────────────────────────┐
│                     Lock 层次结构                              │
│                                                              │
│  Job Lock (job_xxx.json.lock)                                │
│  ├── 保护范围: 整个 Job 的生命周期状态                          │
│  ├── 持有者: Engine                                           │
│  └── 生命周期: 从 Pending 队列取出 → 移动到最终状态目录         │
│                                                              │
│  Task Lock (task_def_N.json.lock)                            │
│  ├── 保护范围: 单个 Task 文件的读写                             │
│  ├── 持有者: Engine (调度) / Task (执行时读取)                  │
│  └── 生命周期: Engine：整个 Task 执行期间                       │
│                Task：写 feedback 时短暂持有                    │
│                                                              │
│  Feedback Lock (job_feedback_xxx.json.lock)                  │
│  ├── 保护范围: Feedback 文件的写入                              │
│  ├── 持有者: Task (进度更新) / Engine (最终状态)                │
│  └── 生命周期: 瞬时（写完即释放）                                │
└──────────────────────────────────────────────────────────────┘
```

#### 2.5.3 Lock 生命周期示例

以一个空三任务从提交到完成的完整流程为例：

```
阶段 1: Job 在 Pending 队列
  Pending/Normal/job_xxx.json  ← 无锁

阶段 2: Engine 获取 Job
  Engine 创建: Pending/Normal/job_xxx.json.lock  ← Engine 持有
  Engine 读取:  job_xxx.json
  Engine 写入:  Running/job_xxx.json
  Engine 删除:  Pending/Normal/job_xxx.json
  Engine 释放:  Pending/Normal/job_xxx.json.lock (移除)

阶段 3: Engine 锁定 Task
  Engine 创建: <项目路径>/task_def_0.json.lock  ← fpTaskLock 持有

阶段 4: Task 进程运行中
  Task 创建:  <项目路径>/job_feedback_xxx.json.lock  ← 瞬时持有
  Task 写入:  job_feedback_xxx.json (更新进度)
  Task 释放:  job_feedback_xxx.json.lock

阶段 5: Task 完成
  Engine 创建: Running/job_xxx.json.lock
  Engine 读取: Running/job_xxx.json
  Engine 写入: Completed/job_xxx.json
  Engine 删除: Running/job_xxx.json
  Engine 释放: Running/job_xxx.json.lock
  Engine 释放: task_def_0.json.lock  ← fpTaskLock 关闭
```

#### 2.5.4 Lock 泄漏与清理

`DoCleanupLockFiles` 线程专门处理**锁泄漏**问题：

```cpp
void DoCleanupLockFiles()
{
    while (true)
    {
        // 遍历 toBeCleanedJobMap（记录所有正在处理的 job）
        for (auto& [jobName, jobPath] : toBeCleanedJobMap)
        {
            // 检查 job 是否已结束（hasFinishedJobMap 中有记录）
            if (hasFinishedJobMap.contains(jobName))
            {
                int state = hasFinishedJobMap[jobName];
                if (state >= 2)  // 已完成/取消/失败
                {
                    // 检查 job 是否已不在 Pending/Running 中
                    // 若已移到 Completed/Cancelled/Failed → 清理残留 lock
                    // 同时清理项目目录下的 .pid 和 .lock 文件
                }
            }
        }
        sleep(1000ms);
    }
}
```

#### 2.7.2 控制台事件处理（HandlerRoutine）

处理 Windows 控制台事件（用户关闭窗口、系统关机等）：

```cpp
BOOL WINAPI HandlerRoutine(DWORD dwCtrlType)
{
    if (CTRL_CLOSE_EVENT == dwCtrlType ||
        CTRL_C_EVENT == dwCtrlType ||
        CTRL_LOGOFF_EVENT == dwCtrlType ||
        CTRL_SHUTDOWN_EVENT == dwCtrlType)
    {
        // 1. 标记退出状态
        bQuitingApplication = true;

        // 2. 导出引擎统计信息
        EngineInfo::Getinstance().ExportEngineInfoJson();

        // 3. 删除引擎注册文件（心跳）
        filesystem::remove(engineinfofile);

        // 4. 如果有正在运行的 Task，杀死子进程
        if (gotNewPendingJobFile || !NewFileForRun.isEmpty())
        {
            killTaskProcess();           // taskkill /f /t /im MoldAITask.exe

            // 5. 将 Job 从 Running 回退到 Pending
            //    （下次引擎启动时可以重新执行，不至于丢失任务）
            jobinfo.tg.feedback.Status = STATUS_PENDDING;
            jobinfo.save(pendingJobPath + jobname);

            // 6. 删除 Running 中的原文件
            AI3D::CORE::File::RemoveFile(runningJobPath + jobname);
        }
    }
    return true;  // 返回 true 阻止系统默认处理
}
```

这个设计确保：
- **引擎异常退出时正在执行的任务不会丢失**：Job 回退到 Pending 队列
- **下次引擎启动后可重新调度**：从 Pending 队列中再次拾取

#### 2.7.3 异常任务监控（searchUnnormaldRunningJobThread）

这个线程持续检测 Running 队列中的异常情况：

```
场景 1: Job 文件丢失，但 Task 仍在运行
  → killTaskProcess() 杀死遗留的 Task 进程
  → 重置 Engine 状态

场景 2: Feedback 文件状态异常
  → 若 feedback 为 CANCEL/FAILURE，但 job 未移到对应目录
  → 杀掉 Task 进程
  → 将 job 移动到 Cancelled 或 Failed 目录

场景 3: Feedback 文件损坏无法读取
  → 杀掉 Task 进程
  → 标记为 Cancel
```

### 3.5 进度回调与反馈机制

#### cbProgress 函数

这是**最频繁被调用的函数**（算法每完成一小步就会调用一次）：

```cpp
void cbProgress(float fvalue)
{
    // 1. 检查 job 文件是否还存在于 Running 目录
    //    （若不存在说明 Engine 已经将 job 移走/删除了）
    if (!filesystem::exists(current_job_file))
        return;

    // 2. 加载当前 feedback 文件
    if (!feedback.load(current_feedback_file))
        return;

    // 3. 检查是否已被取消
    if (feedback.Status == STATUS_CANCLE || feedback.Status == STATUS_FAILURE)
        return;  // 停止更新，让 Engine 处理后续

    // 4. 根据不同 job 类型计算进度百分比
    float currentpercent = 0;
    if (jobtype == JOB_AT)
        currentpercent = curjob.tg.GetProgress(fvalue, current_task_id);
    else if (jobtype == JOB_BATCH)
        currentpercent = fvalue;
    else if (jobtype == JOB_TILE)
        currentpercent = fvalue * 100.0;

    // 5. 只在进度增长时才更新（防止倒退）
    if (progreestemp < currentpercent)
        feedback.Percent = currentpercent;

    // 6. 保存 feedback
    feedback.save_with_retry(current_feedback_file, false);
}
```

**设计要点**：

- **单调递增保护**：`progreestemp < currentpercent` 确保进度只增不减
- **取消检测**：每次回调都检查 feedback 状态，一旦发现被取消即停止更新
- **文件存在性检查**：防止 Engine 已清理了 job 但 Task 还在运行

### 3.6 取消机制

取消流程涉及 Engine 和 Task 两个进程的协作：

```
用户点击"取消"
    │
    ▼
App 层写 feedback.Status = CANCEL
    │
    ▼
Engine (execEngineTimeThread 或其他线程)
    检测到 feedback.Status == CANCEL
    │
    ▼
ExecTaskPostHandle("cancel", taskfile)
    → 启动 MoldAITask.exe cancel <taskfile>
    │
    ▼
Task (execCancelCommandOnly)
    1. 解析 task 文件
    2. 找到 algorithm function
    3. 调用 RunCancel(json, cb)
    4. 设置 GShoudStop = true
    │
    ▼
算法层检测到 GShoudStop == true
    算法提前退出
    │
    ▼
cbProgress 检测到 Cancel 状态 → 停止写 feedback
    │
    ▼
execTaskFile2Only 返回 MOLDAI_USER_CANCEL → 进程退出
    │
    ▼
Engine 检测到退出码 MOLDAI_USER_CANCEL
    → job: Running/ → Cancelled/
    → feedback.Status = CANCEL
```

## 6. 设计模式与技术要点

### 6.1 文件系统作为 IPC 机制

选择文件系统而非 Socket/Pipe/共享内存作为进程间通信方式：

**优点**：
- **可调试性极强**：任何时刻都可以查看文件内容了解当前状态
- **天然持久化**：即使两个进程都崩溃，状态信息也不会丢失
- **无序列化开销**：文件本身就是序列化格式
- **跨平台一致**：文件系统语义在所有平台上行为一致

**缺点**：
- **延迟高**：磁盘 I/O 比内存 IPC 慢几个数量级
- **需要 Lock 机制**：并发写需要额外的文件锁
- **清理负担**：异常退出时可能残留垃圾文件
- **轮询开销**：Engine 需要不断扫描文件系统

### 6.2 基于文件锁的互斥

```
设计原则:
  - 写前加锁，写完释放
  - 锁文件 = 原文件名 + ".lock"
  - 使用 Windows 文件共享模式实现排他写
  - 持锁时间尽量短（瞬时锁），避免死锁
  - 专门的清理线程防止锁泄漏
```

这个设计相当于在文件系统上实现了一个简单的**分布式锁管理器**。

### 6.3 进程级任务隔离

每个 Task 作为独立进程运行的优势：

- **内存隔离**：Task 崩溃不会污染 Engine 内存空间
- **资源回收**：操作系统自动回收 Task 的所有资源（内存、句柄、GPU）
- **独立的错误处理**：Task 的 SEH + signal 处理完全独立
- **可独立调试**：可以单独启动 Task 进程进行调试

### 6.4 崩溃安全设计

Engine 采用了多层崩溃防护：

```
Layer 1: 子进程隔离
  Task 崩溃 → 只有 Task 挂掉，Engine 不受影响

Layer 2: MiniDump 转储
  任何未处理异常 → 自动生成 .dmp 文件 → 可供事后分析

Layer 3: 任务回退
  Engine 崩溃 → running 中的 job 被回退到 pending → 重启后可恢复

Layer 4: 锁清理
  DoCleanupJobLockOnceWhileEngineStart() → 启动时清理孤儿锁
  DoCleanupLockFiles() → 运行时定期清理
```

### 6.5 进度计算的单调性保证

```cpp
// 只在进度增长时才更新，确保在前端展示时进度条不会倒退
if (progreestemp < currentpercent)
{
    feedback.Percent = currentpercent;
}
else
{
    feedback.Percent = progreestemp;  // 保留旧值
}
```

这解决了什么问题？
- 如果 Task 进程重启后重新执行，`cbProgress` 会从 0% 开始回调
- 如果不做单调性保护，feedback 进度会从 100% 跳回 0%
- 前端（App）看到的进度条会"倒退"，用户体验极差

## 7. 代码质量问题与改进建议

### 7.1 严重问题

#### 1. 代码重复

**问题**：`XLog` 类在 [CallEngine.h](Engine/CallEngine.h) 和 [MoldAITask.h](Task/MoldAITask.h) 中**完全相同**（约 50 行），[MyrapidJson.cpp](Engine/MyrapidJson.cpp) 在两个模块中**逐字重复**（约 137 行），CMakeLists.txt 也有大量重叠。

**影响**：Bug 修复需要在两处同步，容易遗漏。

**建议**：将公共代码提取到 `App/Common/` 目录或现有的 `include/` 公共库中。

#### 2. 全局变量竞态条件

**问题**：5 个线程同时读写全局变量（如 `gotNewPendingJobFile`, `fpTaskLock`, `taskrunning`），没有任何同步机制。

```cpp
// Thread 1 (searchPendingJobThread2) 写
gotNewPendingJobFile = true;

// Thread 2 (searchUnnormaldRunningJobThread) 读
if (!gotNewPendingJobFile) { ... }

// Thread 3 (execTaskTimeThread) 读
if (taskPid == -1 || !gotNewPendingJobFile) { ... }
```

**建议**：使用 `std::atomic<bool>` 替换这些标志位，或引入 mutex 保护关键区。

#### 3. 使用 goto 语句

**问题**：[CallEngine.cpp 第 729-733 行](Engine/CallEngine.cpp#L729)：

```cpp
if (!bSuccessful && retry_more_times && retryTimes < 3)
{
    std::this_thread::sleep_for(std::chrono::milliseconds(2000));
    goto Retry_It;  // ← 跳回函数开头重试
}
```

**建议**：将重试逻辑封装为 `do-while` 循环或独立的重试函数。

#### 4. 硬编码路径

**问题**：[BootProbe.cpp 第 14-15 行](Engine/BootProbe.cpp#L14)：

```cpp
const char* logPath =
    "C:\\Users\\Microsoft\\Code\\front_end\\3d_build_C17\\MoldAI\\Bin\\x64\\Release\\engine_boot_probe.log";
```

**建议**：使用环境变量或配置文件指定路径，或使用相对路径。

#### 5. 内存泄漏

**问题 1**：`ATPreprocessTask.cpp` 第 33 行：

```cpp
int* progress = new int(0);  // 从未 delete
```

**问题 2**：`CallEngine.cpp` 第 4988 行：

```cpp
msgBoxThread = new MsgBoxThread(nullptr);  // 从未 delete
```

#### 6. 空异常处理

**问题**：大量 `catch(...)` 块为空，吞掉了所有异常信息：

```cpp
catch (std::exception& ex) { }  // 空的
catch (...) { }                  // 空的
```

**建议**：至少记录日志，帮助诊断问题。

### 7.2 中等问题

#### 1. 线程管理不规范

所有线程使用 `detach()` 而非 `join()`，无法保证退出顺序：

```cpp
std::thread searchPendingJob1(searchPendingJobThread2);
searchPendingJob1.detach();  // 线程独立运行，main 退出时可能被强行终止
```

**建议**：使用 `std::jthread`（C++20）或在退出前通过 `bQuitingApplication` 标志 + `join()` 优雅关闭。

#### 2. 函数过长

| 函数 | 行数 | 建议 |
|------|------|------|
| `ExecTaskFileV2` | ~900 | 拆分为多个阶段函数 |
| `ProcessUnnormaldRunningJob` | ~320 | 拆分条件分支 |
| `GetRunningTaskInRunningJob` | ~230 | 提取重复的 lock 逻辑 |
| `main` (Engine) | ~230 | 提取初始化阶段 |

#### 3. 字符串编码混乱

项目同时使用多种字符串类型和编码转换：

```cpp
std::string → QString: str2qstr(), QString::fromStdString()
QString → std::string: qstr2str(), QString::toStdString()
UTF-8 ↔ GBK: UTF82GBK()  // 注释掉的
char* → std::string: 隐式转换
```

**建议**：统一使用 UTF-8 + `std::string` 或统一使用 `QString`，减少转换函数的种类。

#### 4. Magic Number 散落

```cpp
Sleep(30);    // 为什么是 30ms？
Sleep(50);    // 为什么是 50ms？
Sleep(100);   // 为什么是 100ms？
Sleep(500);   // 为什么是 500ms？
Sleep(1000);  // 为什么是 1s？
Sleep(2000);  // 为什么是 2s？
```

**建议**：定义命名常量 `constexpr auto LOCK_RETRY_DELAY_MS = 100;` 等。

#### 5. 依赖 Win32 过深

大量 `#ifdef WIN32` / `#ifdef _MSC_VER` / `#include <Windows.h>`，跨平台移植困难。

### 7.3 轻度问题

- **注释质量参差不齐**：中英文混用，部分注释过时
- **命名不一致**：`ATLASTTASKTYPE` vs `ATCOMPLETETYPE`，`blk_status_str` vs `jobsta_e`
- **死代码**：大量 `#if 0` 块和空函数体
- **`.cpp_bak` 文件**：`CallEngine .cpp_bak`（169KB）和 `MokTask.cpp_bak` 未清理
- **缺乏单元测试**：整个模块无任何测试代码
